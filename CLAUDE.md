- **Déconnexion Google intermittente — corrigée (2026-09-05)** : `AuthProvider.authBridge.refresh` effaçait la session locale sur **toute** erreur de `refreshAccessToken` (y compris panne réseau/serveur transitoire côté Stack Auth, sans lien avec un refresh token réellement invalide) ; `client.ts` forçait en plus un second `onSignedOut()` dès que `refresh()` renvoyait `null`. `StackAuthError` porte maintenant le statut HTTP d'origine ; `isDefinitiveAuthFailure(err)` (`apps/mobile/src/auth/authError.ts`, extrait de `stackClient.ts` pour rester testable — comme `jwt.ts`) ne renvoie `true` (déconnexion légitime) que pour un 4xx hors 429 ; réseau/5xx/429 = transitoire, session conservée. `client.ts` ne force plus `onSignedOut()` sur un `refresh()` `null` — la décision appartient à `AuthProvider` seul. Test : `apps/mobile/test/authError.test.ts` (5 tests).
  - **Session perdue à chaque MAJ de l'app — corrigée (2026-09-06)** : symptôme distinct du précédent — après un `adb install -r` (ou une MAJ Play Store), l'app repart sur l'écran de login alors que `firstInstallTime` est préservé (donc **vraie MAJ, pas un wipe**) ; un simple redémarrage (force-stop) garde la session, seule la MAJ la perd. Cause : `expo-secure-store` chiffre la session avec une clé AES de l'**AndroidKeyStore** (jamais sauvegardée) ; le manifeste avait `android:allowBackup="true"` et — surtout — **pas** de `android:dataExtractionRules` (Android 12+ ; le device est en Android 16, `fullBackupContent` seul = Android ≤ 11, inopérant). Résultat : les SharedPreferences `SecureStore` étaient éligibles au cloud-backup / device-transfer et une restauration réécrivait le chiffré par-dessus l'install fraîche → clé ≠ chiffré → `BadPaddingException` → `getItemAsync` renvoie `null` → login. (Le module Android le dit texto : *« a new key was generated, but the entries are encrypted using the old one. This usually means that the user has reinstalled the app »*.) Fix : `app.config.ts` → `android.allowBackup = false` **+** re-`expo prebuild` avec l'expo-secure-store courant qui pose maintenant `dataExtractionRules="@xml/secure_store_data_extraction_rules"` (exclut `sharedpref path="SecureStore"` de `cloud-backup` **et** `device-transfer`) ; `AuthProvider` : `SecureStore.getItemAsync(KEY).catch(() => null)` au démarrage (une exception de déchiffrement ne doit pas bloquer sur `'loading'` → spinner infini). ⚠️ Un **vrai** uninstall/réinstall ou une restauration usine demandera toujours une reconnexion (normal, chiffrement). Nécessite un rebuild APK (manifest).
  - **Effet de bord auto-infligé, corrigé le jour même** : le fix ci-dessus a exposé que `fetch()` n'a **aucun délai par défaut** — un rafraîchissement bloqué réseau (jamais de réponse) gelait l'écran **indéfiniment** (reproduit en direct : `GET /repair-guide`, pourtant en cache, resté bloqué plusieurs minutes, `wrangler tail` muet malgré le spinner toujours animé). Fix : `apps/mobile/src/lib/fetchTimeout.ts` (`fetchWithTimeout`, `AbortController`) — 15 s sur les appels Stack Auth (`stackClient.ts`, `oauth.ts`, censés être quasi instantanés), 90 s en filet de sécurité sur `client.ts` (généreux exprès : un diagnostic IA peut légitimement prendre « jusqu'à une minute »). Test : `apps/mobile/test/fetchTimeout.test.ts` (2 tests).

Les deux vérifiés en direct sur device après fix.
- **Type MIME des uploads — vrai fix (2026-09-05, après test sur device réel)** : le fix du 2026-09-04 (normalisation JS + header explicite dans `packages/shared/src/media.ts`) ne suffisait pas — **inutile en pratique**, car sur Android **et** iOS, le pont natif React Native ignore le header HTTP JS pour un body `Blob` : Android `BlobModule.kt#toRequestBody` et iOS `RCTBlobManager.mm#resolveMultipartBlock` lisent en priorité le **type interne du Blob** (`blob.data.type`, dérivé par l'OS — `ContentResolver.getType()` / UTI) et l'utilisent comme Content-Type réel, écrasant silencieusement notre valeur dès qu'il est non vide. Constaté sur un OPPO CPH2799 (Android 16/ColorOS, via `wrangler tail --format json` sur le Worker prod) : le type OS-fourni était invalide pour `MediaType.parse` d'OkHttp → **aucun** Content-Type envoyé → 415 malgré le header JS correct. Fix réel : `apps/mobile/src/api/uploads.ts` → `retag(blob, contentType)` = `blob.slice(0, blob.size, contentType)` (API standard `Blob.prototype.slice`, RN core) crée une nouvelle vue sur les mêmes octets avec le type qu'on lui donne, qui devient alors ce que lit le pont natif — sur les deux plateformes. `packages/shared/src/media.ts` reste utile (calcule quel type canonique passer), mais l'ancien mécanisme seul (header + `blob.type`) ne corrigeait rien pour un type OS non vide et invalide.
- **Clavier qui masque la saisie — vrai fix (2026-09-05, après test sur device réel)** : le fix du 2026-09-04 (`Screen.keyboardAware` + `KeyboardAvoidingView behavior="height"` sur Android) ne faisait **rien** — vérifié via `dumpsys window`/`uiautomator` : l'`EditText` restait entièrement sous le clavier. Cause : le calcul interne de `KeyboardAvoidingView` (`frame.y + frame.height - keyboardY`) suppose `frame.y` (mesuré par `onLayout`, **relatif au parent**) absolu à l'écran — faux dès que la vue est nichée dans un `SafeAreaView`, et aggravé sous edge-to-edge (Android 15+, `edgeToEdgeEnabled=true` par défaut sur Expo/RN récents) où le résultat est une hauteur quasi nulle, quel que soit le `behavior`. Fix réel : `Screen.tsx` abandonne `KeyboardAvoidingView` — écoute directement `Keyboard.addListener('keyboardDidShow'/'keyboardDidHide')` (mécanisme RN moderne basé sur `WindowInsetsCompat.Type.ime()`, `ReactRootView.java#checkForKeyboardEvents`, robuste à l'edge-to-edge) pour ne récupérer que la **hauteur** du clavier (valeur absolue, aucune ambiguïté de repère), l'ajoute en `paddingBottom` du contenu du `ScrollView` interne, et appelle `scrollToEnd()` automatiquement à l'apparition du clavier — centralisé dans `Screen`, plus besoin de hack par écran (`describe.tsx`, `CaptureFlow` en profitent sans code supplémentaire ; l'ancien hack `onFocus`+`setTimeout` de `CaptureFlow` est supprimé).
  - **Leçon** : ces deux bugs avaient été déclarés corrigés le 2026-09-04 sur la seule foi d'une relecture de code + tests unitaires verts — **les deux étaient toujours cassés**. Ni la relecture ni Vitest/Node ne peuvent attraper un comportement spécifique au pont natif Android/iOS (RN `Blob`/`KeyboardAvoidingView`) ou à un OEM particulier (edge-to-edge ColorOS, `ContentResolver.getType()`). Diagnostiqué en confirmant sur le device réel de l'utilisateur (branché en USB) via `adb`/`uiautomator2` (tap, screenshot, dump de vues) + `wrangler tail --format json` (requête HTTP réelle reçue par le Worker prod — le format `pretty` de `wrangler tail` affiche `- Ok` pour signifier « pas d'exception », **pas** le code HTTP réel : piège à connaître). Avant d'annoncer un fix mobile résolu, le vérifier sur un device physique quand c'est possible, pas seulement par la relecture/les tests.
- **Pannes IA** : `AIProviderErrorCode` = `ai_request_failed` (502) · `ai_rate_limited` (429, quota) · `ai_overloaded` (503, « high demand » — **rencontré en vrai**) · `ai_bad_output` (422). 429 **et** 503 déclenchent la bascule de modèle. ## Build mobile (Android, local)

`android/` et `ios/` sont **gitignore** (générés par `expo prebuild`). Prérequis machine :
- `pnpm` **11** ignore `.npmrc` pour ses réglages → `nodeLinker: hoisted` + `shamefullyHoist: true` sont dans `pnpm-workspace.yaml`. Vérif : `pnpm config get node-linker` → `hoisted`. Sinon `babel-preset-expo` (et autres deps transitives) introuvables au bundling.
- **NDK `27.1.12297006` (r27b)** requis par RN 0.86 — installé manuellement dans `~/Library/Android/sdk/ndk/` (pas de `cmdline-tools` → AGP ne peut pas l'auto-télécharger).
- `JAVA_HOME` = **openjdk@17** (pas 21). `ANDROID_HOME=~/Library/Android/sdk`.

**Changement JS/assets uniquement** (pas de nouvelle dép native, pas de plugin `app.config.ts`) : sauter `expo prebuild`, juste `cd apps/mobile/android && ./gradlew :app:assembleRelease -x lint -PreactNativeArchitectures=arm64-v8a` (avec les `export` ci-dessous). Metro re-bundle le JS + les assets. Fait le 2026-09-02 pour le guide illustré (~19 min, daemon froid).

Build APK release from scratch / nouveau module natif (signé avec la clé debug → installable, JS bundlé) :
```
cd apps/mobile && npx expo prebuild --platform android --clean --no-install
git checkout apps/mobile/package.json   # prebuild remplace les scripts android/ios par `expo run:*`
cd android
export ANDROID_HOME=~/Library/Android/sdk \
  JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home \
  EXPO_PUBLIC_APP_ENV=production
./gradlew :app:assembleRelease -x lint -PreactNativeArchitectures=arm64-v8a --console=plain
# → app/build/outputs/apk/release/app-release.apk  (~52 Mo arm64 seul)
```
Temps de build **mesuré 2026-09-02** avec le script : **45 s** pour un rebuild où rien n'a changé (`compileReleaseKotlin` UP-TO-DATE, lintVital sauté, 25/337 tâches) — vs **~19 min** juste avant, même état, avec `daemon=false` + lintVital. Attendu : **~2-4 min** pour un vrai changement JS/assets (rebundle Metro + hermesc) ; **~10-15 min** pour `--clean`/nouveau module natif. Ne pas supprimer `~/.gradle`, le NDK, ni `apps/mobile/android/{.gradle,build,app/build}` entre deux builds (cf. [[build-cache-protection]]). L'APK (~52 Mo) dépasse la limite d'upload du chat (30 Mo) → `open -R` (le script le fait).

**Boucle rapide pour itérer sur le JS** (pas de rebuild APK) : garder l'APK debug/release installé + `pnpm mobile` (Metro) — le JS se recharge à chaud. Le rebuild APK ne sert que pour livrer une version installable autonome.
NB : `git checkout apps/mobile/package.json` après `prebuild` ne fait que restaurer les scripts `android`/`ios` ; les vraies deps (dont `expo-video`) sont déjà committées.
APK léger (~arm64 + R8) : dans `android/gradle.properties` poser `reactNativeArchitectures=arm64-v8a`,
`android.enableMinifyInReleaseBuilds=true`, `android.enableShrinkResourcesInReleaseBuilds=true`.
`EXPO_PUBLIC_APP_ENV=production` est **impératif** pour OAuth (redirect_uri `/auth/callback` doit être joignable depuis le navigateur système). `eas.json` a des profils prêts si EAS est installé un jour.
Tester OAuth : impossible en Expo Go (schéma natif `fixitai://`) → dev-client ou APK.
